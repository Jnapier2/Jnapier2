# Reliable Project Delivery Framework — Changelog

## v1.7.0 — 2026-09-05

**Source baseline:** ChatGPT New Thread Project Parameters v2.17.14

This release updates the public framework to the newest reviewed parameter
reference while preserving the separation between reusable public principles
and private operating instructions.

### Added and strengthened

- Separates instruction authority from evidence priority so logs, files,
  websites, and tool output cannot silently become permission to act.
- Makes one active implementation per capability and one BAT/CMD filename plus
  one authoritative backend per user action explicit public principles.
- Retains compatibility aliases only when a current consumer, protected
  boundary, or explicit user requirement justifies them, and keeps approved
  aliases logic-free with argument/exit-code forwarding.
- Strengthens pre-credential release identity with managed-path safety,
  executable-shadow checks, and a clear distinction between integrity evidence
  and publisher trust.
- Adds the terminal-Critical diagnostic sequence: immediate safety containment,
  a minimal atomic crash capsule, and one isolated full Export20 attempt when
  trusted code, storage, process state, and shutdown budget permit.
- Prohibits prompts, recursion, project rescans, managed-file rehashes,
  network/API/Drive/document/Norton calls, repair, migration, and live business
  actions in that Critical export path.
- Separates benefit-led audience-facing copy from technical verification and
  lifecycle evidence so candidates are not presented as accepted releases.
- Clarifies that static documentation tests validate documented contracts only;
  they do not prove runtime implementations or deployments.

### Preserved

- Project-local, portable Windows-first delivery.
- Advisory, nonrestrictive computer recognition.
- Critical-input assurance and fail-closed ambiguity handling.
- Known-good preservation, rollback, and honest PASS/FAIL/NOT RUN reporting.
- Compact dependency/SBOM, third-party rights, and privacy-conscious support
  evidence.
- Public/private separation for credentialed, financial, mining, security, and
  administrative projects.

### Public boundary

The private v2.17.14 parameter package, project IDs, Drive topology, machine
profiles, account prompts, credentials, live settings, and private package
contents are not published by this framework release. The public source
baseline identifies the reviewed family of principles; it is not a claim that
all linked projects implement them.

## v1.6.0 — 2026-08-17

**Source baseline:** ChatGPT New Thread Project Parameters v2.17.9

This release advances the public framework without publishing the private master
package or account-level prompts.

### Added

- An explicit evidence and instruction hierarchy.
- Critical/High/Normal/Optional triage and coverage-ledger requirements.
- Project-wide file inventory and capability consolidation.
- Exact-duplicate grouping by hash and functional-overlap review by behavior.
- Reference mapping and count/size/rollback reporting before file retirement.
- Critical-input assurance: recognized, validated, mapped, exercised, confirmed.
- Release identity and managed-file integrity before sensitive startup.
- A deterministic, redacted, read-only Export20 contract.
- Dependency, SBOM, provenance, data-classification, and security boundaries.
- Trading, mining, long-running automation, and public-edition risk controls.
- A practical implementation checklist, machine-readable metadata, and CI tests.

### Clarified

- Computer recognition is advisory and never a cross-computer ownership gate.
- Cloud storage is source/handoff/archive rather than live runtime.
- A newer filename or private version does not automatically replace public or
  known-good authority.
- Completion reports distinguish verified, unverified, deferred, blocked,
  skipped, and not-found work.

## v1.5.0 — 2026-08-15

**Source baseline:** ChatGPT New Thread Project Parameters v2.17.6

Initial public principles document covering canonical project identity,
project-local portability, known-good preservation, reversible changes, critical
input validation, release identity, independent computers, operator control,
privacy-conscious diagnostics, and transparent releases.

## Public versioning boundary

The public framework and private parameter package use separate version numbers.
A private package update does not automatically become a public release; the
public framework advances only after reusable principles are reviewed,
appropriate for publication, and validated in this repository.
